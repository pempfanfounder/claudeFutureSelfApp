# S4 B04 local server draft

This batch implements the approved local B04 queue/ticket/receipt boundary. It has **not** run against PostgreSQL, Supabase, PGMQ, Deno, Expo, cron, a native app, or any external service. No migration, schedule, quota, secret, commit, push or deployment was performed. The migration starts `push_pipeline_control.paused = true`; source review and synthetic handler fixtures do not authorize unpausing a target.

## Owned changes

- `supabase/functions/push-dispatch/index.ts`: leased SQL protocol, bounded provider call and response parsing, per-device outcomes, fenced/idempotent persistence retries, honest committed counts. Original curated content selection/text is retained. The trial message now says the trial ends soon, without assuming a specific remaining day.
- `supabase/functions/push-receipts/index.ts`: leased per-device receipt batch, bounded transport/parsing, missing receipts remain pending, idempotent finalization, no direct device mutation or raw payload logging.
- `supabase/migrations/20260908012000_s4_push.sql`: additive delivery phase columns, private per-device/schedule/control ledgers, private RPCs, forward replacements for producer wrappers and queue read, bounded retention. Historical migrations/shared helpers/client files were not edited in B04.
- `supabase/tests/s4-push.cjs`, `s4-push-typecheck.cjs`, `s4-push-capacity.cjs`, `s4-push.sql`, this document.

## State and recovery policy

A queue visibility timeout is not proof of exclusive sending. A logical delivery has its own preparation/send lease. Its per-device rows distinguish ready/retry_wait, sending, acknowledged ticket, final receipt, explicit error, skipped, uncertain and exhausted. A receipt update preserves a dispatcher's preparing phase so earlier-ticket completion cannot invalidate a valid send lease for remaining devices.

The handler tries one provider request for an attempt batch. Timeouts, HTTP/parse failures, missing/duplicate tickets or unknown acceptance become **uncertain**, without automatic resend. A crash after begin also becomes uncertain on queue recovery. This intentionally permits a missed notification when a crash occurred before actual transport; exactly-once delivery is not asserted. Persisting a known result may be retried twice with identical values; the provider request is never retried for response loss.

Only an explicit `MessageRateExceeded` ticket rejection is retried automatically, at60/120-second backoff, maximum3 sends while the job remains useful. Other explicit ticket errors end that attempt. Missing/failed receipt lookups remain pending, with15-minute exponential backoff capped4hours. A ticket older24hours or after8 receipt claims becomes `receipt_unresolved`, never a device invalidation. Ticket/receipt success is a provider acknowledgement, not a handset presentation/read guarantee.

`DeviceNotRegistered` invalidates only an exact current device UUID, user UUID, registration_version and token match. The attempt's UUID/version/token are immutable snapshots; deleting or reassigning a current registration does not rewrite that mapping. Rotation, cross-user reassignment, deactivation/reactivation and permission change advance the existing B03 registration version. Account deletion still cascades its owned attempt/delivery rows. Auth-user KEY SHARE and deterministic parent locks precede child mutation in finalization/import/expiry/retention. The two-session deletion/registration protocols remain required; no runtime claim of deadlock freedom is made.

Legacy parent rows are preserved. Legacy queued deliveries are marked uncertain and archived rather than resent. Unanchored legacy trial queue messages are archived: their intended trial cannot be reconstructed safely. Existing legacy ticket IDs are imported at most50/pass as explicitly unmapped attempts; invalid/duplicate legacy IDs receive a bounded error code. Legacy receipts never deactivate a device because the original worker did not reliably retain the target mapping. Tickets lost by the original worker cannot be recovered from a parent record that stored only the first ticket.

A trial reservation is keyed to its actual trial end, not aggregate/grace/lifetime expiry. The producer only reserves it inside the currently allowed send window; midnight/late-night work remains unreserved for a later eligible pass. Queue TTL is6hours and the send must remain on its originally scheduled local day. Changes after reservation can therefore skip work rather than move its meaning to another day.

## Bounded local policies and limits

These are conservative local draft values, not production capacity or spend evidence:

- 40-second dispatcher deadline, per-query/RPC abort within3seconds and within the remaining deadline,8-second provider abort, at least18seconds left before starting a send. SQL preparation lease45seconds, send lease30seconds. Receipt RPC abort5seconds and provider abort8seconds. Actual SDK cancellation behavior is not verified.
- New jobs:8 global reservations/minute; device sends:8/user and8/global per fixed minute; scheduler/reader/receipt calls:2 global per minute each. One active dispatch lease globally; one receipt batch globally. Fixed-minute buckets permit boundary bursts; these are not rolling limits.
- Queue cap100; pending receipts cap600; oldest unresolved receipt beyond2hours blocks new sending. Batch headroom prevents a599→607 overshoot. Admission denial does not advance schedule counters or consume a trial anchor. Existing counter names describe reserved slots, not delivered notifications.
- Terminal attempt retention30days, uncertain evidence90days, new terminal parent and schedule idempotency retention90days, marked new queue archive retention30days. At most200 rows of each category retire per receipt-consumer pass. Active rows and legacy parent/archive history are preserved. Current device/authored records are never retention targets. Token copies retire with their attempt rows or their owner's account deletion.

Selected source cron cadence is enqueue every5minutes, dispatch everyminute, receipts every15minutes and trial selection hourly. No cadence is changed here. The independent four-hour arithmetic fixture assumes an explicitly unpaused one-job-per-device stress case with8 new jobs/minute: healthy receipt acknowledgements peak at232 pending, while an outage stops sending at600 pending and admission at100 queued. This proves only the arithmetic model's bounds. Multi-device fanout, DB scan/lock time, actual provider latency/errors, cron drift, retries, cold starts, abuse traffic and storage costs are not measured; no100k-user/free-tier claim follows from it.
